## 배경

사내 산재된 문서 데이터를 효율적으로 탐색할 수 있는 서비스 필요, 문서 검색 정확도 최적화가 과제

## 접근

오픈소스 벡터DB 자체 구축도 고려했다가 AWS Bedrock으로 선회

- **관리 부담** — 오픈소스는 인프라 구축/운영(스케일링, 장애 대응, 버전 관리) 직접 부담, Bedrock은 Knowledge Base로 벡터화·인덱싱·검색을 매니지드로 제공
- **보안/네트워크** — Bedrock은 VPC 엔드포인트로 AWS 내부 폐쇄망 구성 용이, 오픈소스는 별도 인프라에 자체 보안 설정 필요
- **비용 구조** — 오픈소스는 인프라 상시 운영 비용 발생, Bedrock은 사용량 기반 과금으로 초기 부담 적음

청킹 사이즈는 여러 값으로 조정하며 검색 결과물 만족도 기준으로 1,000 확정
LLM은 Claude 3 Sonnet/Haiku 등 당시 시점 기준 가용한 모델 중 채택, 응답 속도와 추론 복잡도에 따라 교차 활용

## 구현

- **RAG 아키텍처 최적화** — AWS Bedrock 및 RAG(Retrieval-Augmented Generation) 아키텍처를 활용한 사내 지식 베이스 기반 생성형 AI 챗봇 구축, Amazon Titan 모델로 문서 벡터화 및 청킹 사이즈 1,000 설정 → 검색 정밀도 향상
- **성능 밸런싱** — Claude 3 Sonnet과 Haiku를 교차 활용(빠르고 복합적인 추론 방식 추구)
- **엔터프라이즈 보안 구현** — VPC 엔드포인트를 통한 네트워크 격리
- **운영 자동화** — 초기 ECS 기반으로 설계했다가 이후 EC2 단일 인스턴스로 변경, 서비스 가용성 확보
- **성능 모니터링** — TunA 활용 (실시간 서비스 지표 관제 체계 구축)

## 결과

기능 구현 및 초기 테스트까지 진행 후 퇴사로 프로젝트 인계
정량적 성과 지표(검색 정확도, 응답 시간 등)는 측정 전 단계에서 마무리
