## 배경

기존 인프라가 관리형 노드그룹 19개로 과도하게 파편화되어 있어, 실제 워크로드 사용량 대비 운영 비용이 비정상적으로 높게 발생
리소스 생성이 콘솔을 통한 수동 작업 위주, VPC·서브넷 외에는 IaC 미전환 상태라 초기 구성 이력 파악 어려움
구성 관리 개선과 운영 리스크 감소도 필요

## 접근

Kubecost 및 k9s로 시스템별 리소스 사용률을 정밀 분석해서 노드그룹 통합을 통한 비용 절감 로드맵을 선제적으로 제안 → 노드그룹 19개를 5개로 축소
수동 운영 방식을 탈피하기 위해 Terraform 및 YAML 기반의 코드로 인프라를 정의, 배포 속도를 높이고 버전 관리가 가능한 환경으로 설계
오토스케일링 방식은 비용·확장 속도 측면에서 유리하다고 보고 Karpenter 도입을 직접 제안했다가 철수, 일반 ASG(Cluster Autoscaler) 유지로 결정
제주항공 이벤트는 제한된 수량을 구매하려는 트래픽이 짧은 시간 동안 폭주하는 패턴이라, 노드를 작게 유지하다 빠르게 스케일하는 비용 최적화보다 Replica Set을 사전에 넉넉히 확보해 서비스 안정성을 우선하는 쪽이 낫다고 회의를 거쳐 결론, 비용 일부 포기

## 구현

- **노드그룹 최적화** — 파드(Pod)의 QoS 설정을 조정해 자원 할당 효율을 극대화, 기존 19개의 노드그룹을 5개로 통합·축소
- **불필요 리소스 정제** — 운영 중 누적된 미사용 보안그룹(SG), 로드밸런서(LB), EBS 볼륨 등을 전수 조사해 삭제, 클라우드 자원의 낭비 요소 제거
- **모니터링** — 최적화 상태를 추적할 수 있는 대시보드 구축 (Kubecost, Prometheus)
- **비용 절감** — 기술적 최적화를 통해 월평균 약 2,500만원(연간 약 3억원 규모)의 운영 비용 절감

### EKS 1.32 업그레이드 (Blue/Green)

in-place 대신 1.32 신규 클러스터를 따로 만들고 트래픽을 옮기는 방식 채택
EKS 컨트롤 플레인은 한 번 올리면 되돌릴 수 없고, 한 마이너씩 올려야 해서 in-place면 되돌릴 수 없는 변경이 여러 번 쌓임 → 신규 클러스터를 옆에 두고 도메인만 전환하는 쪽이 안전하다고 판단
클러스터 두 개 병행 운영 비용과 전환 시점의 짧은 점검 시간은 감수

1. 2024.12 업그레이드 계획 수립(당초 1.31 기준)
2. 개발계에 신규 클러스터 먼저 구성, 서비스별 검증리스트로 확인
3. 2025.02.18 새벽 운영계 전환: 기존 서비스 차단 → 신규 클러스터 LB 도메인 전환 → Akamai 도메인 변경 → 검증리스트로 전체 API 확인 → 차단 해제
4. 원복 방안: 문제 시 도메인을 기존 클러스터로 되돌림

신규 클러스터로 옮기면서 매니페스트에 namespace 지정, ALB target-type을 IP로 변경
통합 전 구성은 서비스마다 `eks.amazonaws.com/nodegroup` nodeAffinity로 전용 노드그룹에 고정된 구조였고, 신규 클러스터를 만드는 김에 노드그룹을 WEB, WAS, PAE, OTA 단위로 재설계

- 통합 후 5개 구성: WEB / WAS / PAE / OTA / 애드온
- PAE·OTA 별도 노드그룹 유지: 보안상 분리 + 외부 API 연계가 많은 업무라 격리 (당시 이해 기준, 정확한 결정 근거는 미확인)
- 통합 후 affinity 키를 `eks.amazonaws.com/nodegroup` 그대로 썼는지 커스텀 라벨로 바꿨는지는 기록 없음

### 운영 중 매니페스트 구성 (홈페이지 WAS 기준)

- **배포 방식** — Jenkins가 `#Edit to ...` 주석이 달린 템플릿 매니페스트에 이미지 태그를 넣어 `kubectl apply`, `revisionHistoryLimit: 1`
- **스케일링** — Deployment에 replicas 없이 HPA(min 20, max 60, CPU 40%)로 운영
- **프로브** — readiness 10초 간격·5회 실패, liveness 30초 간격·timeout 30초·3회 실패·`initialDelaySeconds: 600`, 둘 다 DB를 거치지 않는 `ready.html`만 확인
- **무중단 종료** — `maxUnavailable: 0`, preStop에서 30초 대기 → `ready.html` 삭제 → 120초 대기, `terminationGracePeriodSeconds: 240`
- **개선 필요** — WAS 관리 서버 키와 라이선스 코드가 ConfigMap에 평문으로 존재

### 운영 중 겪은 장애 유형

- **OOMKilled로 인한 CrashLoopBackOff** — 메모리 limit 초과가 원인, `kubectl describe pod`의 Last State로 프로브 문제와 구분
- **노드 자원 부족 Evicted** — 노드 메모리 부족, 디스크 부족 두 경우 모두 발생

### 리소스 분석 도구

Kubecost, kube-prometheus-stack, kube-state-metrics, Robusta(KRR)를 리소스 사용량 분석 용도로 Helm으로 잠깐 설치해 사용

## 결과

- 노드그룹 19개 → 5개로 통합
- 유휴 리소스 비율 60%대 → 10%대로 감소
- 월평균 약 2,500만원(연간 약 3억원 규모) 운영 비용 절감
- 2025.02.18 EKS 1.32 신규 클러스터로 운영 전환 완료

## 회고

비용 절감과 동시에 매니징 포인트 대폭 감소, 운영 부담 완화 체감

다만 정리 과정에서 불필요한 보안그룹이 예상보다 많이 발견되어 그간의 리소스 관리 소홀 확인
Terraform 코드 작성도 일정에 쫓겨 중복 리소스가 다수 발생, 추후 리팩토링 필요성 남음

이때 SG를 노드그룹 단위로 들여다보면서, SG 경계가 서비스(업무) 경계와 별개로 노드그룹 단위로 공유 운영되고 있다는 걸 확인
