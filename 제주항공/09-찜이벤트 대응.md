## 배경

2024년 1월 찜 이벤트(1차 국내선 6개 노선, 2차 국제선 37개 노선) 오픈에 맞춰 홈페이지/서치채널/서치엔진/예약엔진(IBE)/FFP/PAY채널/PAY엔진 7개 업무 영역 실시간 모니터링 수행
이벤트 오픈 직후 다수 업무에서 XLOG상 10초 이상 지연 트랜잭션과 Error 트랜잭션이 특정 시간대에 집중 발생
각 업무 담당 입장에서는 "외부 API가 느리다" 수준으로만 인지되던 상태로, WAS 내부 처리/DB/외부 API 중 어느 구간의 문제인지 구분이 안 되는 상황

## 접근

LENA(XLOG 기반 응답시간·서비스 분포 모니터링)로 업무별·시간대별 지연/Error 트랜잭션 우선 스크리닝
지연·Error로 잡힌 트랜잭션은 TunA(스레드덤프 분석)로 넘겨 Runnable Thread Stack까지 추적 — "느리다"가 아니라 어느 메서드에서 대기 중인지 특정하는 방향으로 접근
7개 업무를 1차(국내선)/2차(국제선) 구간으로 나눠 순차 분석, 반복되는 Error 메시지를 유형별로 분류

## 구현

- XLOG 상태로 업무별 응답시간 분포 확인 → 업무별 지연 임계치(3초/5초/10초 등) 초과 구간 특정
- Error는 예외 메시지 기준 원인 분류
  - 클라이언트 취소 : `ClientAbortException`
  - API 소켓 타임아웃 : `Read timed out`, `Connection reset`, `failed to respond`
  - 커넥션 타임아웃 : `ConnectException: Connection timed out`
- TunA 스레드덤프로 지연 트랜잭션의 Runnable Thread Stack 확인 → 대부분 `SocketInputStream.socketRead0`, `tomcat.jni.Socket.recvb` 등 소켓 대기 상태로 확인, 자체 WAS/DB 처리 지연이 아니라 외부 API 응답 대기로 판단
- 예외 케이스 별도 식별 : 서치엔진의 특정 INSERT SQL 지연, FFP의 PK 무결성 제약 위반(`ORA-00001`), PAY엔진의 대량 resultset 조회 경고(`over #10000`)
- 업무별 XLOG 상태 / Error 상세 / 지연 상세로 나눠 분석 결과 보고서화

## 결과

7개 업무 영역 전반에 반복되던 지연 원인을 "외부 API(`api.jejuair.net`) 응답 지연/타임아웃"으로 특정 — 업무별로 개별 원인불명 이슈로 흩어져 있던 현상을 공통 원인으로 통합 진단
예약엔진·FFP는 2차(국제선) 구간에서 실제 유입 차단(트래픽 제한) 조치로 대응한 이력 확인

이후 시점(2025년) 기준 AWS 운영시스템 구성정의서를 보면 API 트래픽이 전용 EC2 풀(외부연계/외부유입 분리) · 3단 NLB · 전용 방화벽 · 전용 Repository DB · 전용 로그 수집 경로로 분리된 API GW(API Connect) 구조로 존재
다만 이 구조 도입이 본 분석의 직접적 후속 조치였는지는 워크로그 등 별도 기록으로 확인되지 않음, 시점상 선후관계만 확인됨 (인과관계 아님)

## 회고

업무별로 흩어져 보고되던 지연/Error 현상을 LENA(거시적 응답시간 분포)와 TunA(미시적 스레드 분석)로 조합해 공통 원인으로 수렴시킨 점은 성과
분석 결과가 실제 어떤 개선조치로 이어졌는지 뒷받침할 기록이 남아있지 않은 점은 아쉬움 — 트러블슈팅 결과와 후속 조치를 연결해 기록하는 절차 부재
다음 장애/이벤트 대응부터는 분석 결과와 후속 조치를 워크로그에 명시적으로 연결해 인과관계를 추적 가능하게 남길 필요
