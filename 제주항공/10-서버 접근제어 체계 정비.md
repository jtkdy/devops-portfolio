## 배경

폐쇄망 환경이라 개발자·협력사 서버 접근제어(AD·SAC)는 초기부터 갖춰진 상태
EKS 클러스터 애드온(ALB Controller, EBS CSI, Cluster Autoscaler)이 AWS API 호출 필요, 노드 Role에 권한을 몰아주지 않고 애드온별 분리 필요

## 접근

기존 구조 유지: 계정·권한 그룹 관리는 MS Active Directory GPO, 서버 단위 접근 통제는 타사 서버접근제어(SAC) 솔루션으로 이원화된 체계 운영
SAC 솔루션은 자체 구축이 아니라 타사 제품을 운영·관리하는 방식
클러스터 애드온 AWS 권한은 IRSA(IAM Roles for Service Accounts, 서비스어카운트에 IAM Role을 연결해 파드가 임시 자격증명을 받는 방식)로 부여
온프렘 VM의 Jenkins 배포 파이프라인은 배포용 IAM User 인증 그대로 유지, IRSA 적용 대상 아님

## 구현

- MS Active Directory GPO 기반 계정·권한 그룹 관리 운영
- 타사 서버접근제어(SAC) 솔루션 운영·관리
- eksctl `withOIDC: true`로 클러스터 OIDC Provider 등록, `kube-system` 서비스어카운트 3개에 IRSA 적용

| 서비스어카운트 | 애드온 | eksctl wellKnownPolicies |
|---|---|---|
| aws-load-balancer | AWS Load Balancer Controller | awsLoadBalancerController |
| ebs-csi-controller-sa | EBS CSI Driver | ebsCSIController |
| cluster-autoscaler | Cluster Autoscaler | autoScaler |

## 결과

계정(AD)·서버(SAC) 이원 통제 체계 운영
클러스터 애드온 3종은 장기 액세스키·노드 Role 공유 없이 서비스어카운트별 IAM Role로 AWS 접근

## 회고
