## 배경

- [[01-차세대 PSS 프로젝트 EKS 전환|PSS EKS 전환]] 진행되면서 EKS 환경에 대한 백업 체계가 갖춰지지 않은 상태로 운영 중인 것 확인
- 기존 온프레미스 시스템은 NetBackup으로 백업 관리 중이었으나, 하이브리드 환경(온프레미스 + AWS) 전반을 아우르기엔 한계
- 감사/컴플라이언스 대응 관점에서도 백업 보관기간·주기가 시스템별로 표준화되어 있지 않은 상태

## 접근

온프렘 통합로그 서버 구축 및 ELK 설정으로 로그 수집 체계부터 정비
백업 솔루션은 기존 NetBackup에서 NetWorker로 전환하는 방향으로 설정

전환과 별개로 시스템 중요도 구분 작업 진행 — 감사/컴플라이언스 대응 위해 시스템별 백업 보관기간/주기 정책 재정립 필요 판단

물리 서버 OS 이미지는 NetWorker와 분리해 Acronis로 별도 운영
복구 목적이 데이터 복구와 OS 복구로 달라서, 한 솔루션에 묶기보다 나누는 쪽이 보관기간 설계에 유리하다고 판단

## 구현

### 전환

- 2021.12 NetBackup → NetWorker 이관 완료, 백업 설정 구성
- 이후 Acronis 병행 운영 체계로 정착

### 백업 대상 (2024.12 기준, 현황 자료 v3.4)

| 구분 | 규모 | 주기 | 보관기간 |
|---|---|---|---|
| Acronis (물리 OS 이미지) | 138대 (Linux 92 / Windows 46) | daily 136, weekly 2 | 7~15일 |
| NetWorker (물리/OS 정책) | 정책 354건 / 호스트 206대 | daily 295, 1시간 58 | 97일~1년 |
| NetWorker (VM) | 202대 (VM1~VM9 그룹) | 24시간 | — |
| AWS | EC2·EBS | daily | 1개월 |

Acronis 라이선스 150ea 보유, 미사용 서버 정리하며 실사용 138대로 유지

### 등급 체계

- 업무 중요도를 A~D 4등급으로 구분하고 DB/FILE을 나눠 8개 그룹 구성
- 보관기간 분포 — 6개월 121건, 3개월 112건, 8개월 57건, 1년 53건, 97일 9건
- 백업 방식 — Incremental 298건, Archive 45건, Full 11건. 증분 중심에 월 1회 Full 병행(정책별로 매월 8일 등 고정일 지정)

### 스토리지·소산

- 백업 스토리지 3대 약 510TB — 운영 약 250TB, 통합로그 스냅샷 약 85TB, 소산 약 170TB
- 중복제거율 운영 0.98 / 통합로그 0.55 수준
- 매주 월요일 용량 점검, 전일 대비 증감량 기록해 증가 추세 추적
- 소산(DR) 복제본은 업무 등급별 FS/DB와 VMware 기준 6개 그룹으로 관리
- 소산 가용량 확보 작업 — 만료 세이브셋을 그룹별로 추출해 정리 목록 작성(약 34만 건) 후 순차 삭제, VM은 vCenter 단위로 복제본 크기·만료일 대조해 대상 선별

### 문서 관리

- 백업 현황 자료를 v1.0(2021.12) ~ v3.4(2024.12)까지 20여 차례 개정하며 단일 문서로 유지
- 개정 사유 — 미사용 서버 정책 제거, 신규 업무 정책 추가(항공 어드민 VM, WEB/WAS 등), OS 패치 대비 백업 추가, 아카이브 백업 분리, 보관기간 변경

## 결과

- 백업 정책 표준화 완료, 감사/컴플라이언스 대응 근거 확보
- 작업/장애 상황 시 NetWorker·Acronis 기반 백업·복구로 장애 시간 최소화에 기여
- 2021.07~2025.06 약 4년간 백업 대상·정책·용량 현황을 단일 문서로 최신 상태 유지

## 지원 서류 표기 기준

정밀 수치를 그대로 옮기면 자료 덤프처럼 읽혀서, 지원 서류에는 반올림한 값 사용

- 물리 서버 약 140대 / VM 약 200대 / 백업 정책 약 350건
- 백업 스토리지 약 500TB (소산 약 170TB 포함)
- 보관기간 3개월~1년 차등, 증분 중심 + 월 1회 Full
- 소산 만료 세이브셋 정리는 건수 대신 "그룹별 목록화 후 순차 정리"로 서술

## 회고

- 잘된 것 — 솔루션 전환 자체보다 등급·보관기간 정책 재정립이 감사 대응에 더 크게 작용. 등급 체계가 있으니 신규 업무가 들어와도 정책 결정이 빨라짐
- 잘된 것 — 현황 자료를 버전 관리한 덕에 3년 뒤에도 대상·주기·보관기간을 근거와 함께 복원 가능
- 아쉬운 것 — RPO/RTO 목표치를 명시적으로 정의하지 못함. 복구는 장애·작업 요청 시점에 수행하는 방식에 머물렀고 정기 복구 테스트로 검증하는 단계까지는 가지 못함
- 다음에 할 것 — 등급별 RPO/RTO를 먼저 정의하고 분기 1회 복구 테스트를 정례화. 소산 정리도 수동 목록 작성 대신 만료 기준 스크립트로 자동 추출
