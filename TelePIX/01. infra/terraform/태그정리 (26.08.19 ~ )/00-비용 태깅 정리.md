## 배경

Cost Explorer(AWS 비용을 태그·서비스별로 쪼개서 보여주는 대시보드)로 비용을 들여다보려 했는데, 서비스별로도 환경별로도 제대로 분해 불가
몇몇 루트 모듈은 태그가 전혀 없었고, 있는 곳도 루트 모듈마다 붙이는 방식이 제각각
이대로는 "이번 달에 어느 서비스가 비용을 얼마나 썼는지" 같은 가장 기본적인 질문에도 답변 불가
그래서 태깅 전략을 수립하고 코드 전체를 정비하기로 결정

(이 문서에서 실제 서비스명은 A/B/C/D로, AWS 계정 ID·IAM Role명·S3 버킷명 등 리소스 식별자는 용도로 대체해서 기재함)

---

## 접근

먼저 리포 전체에 Terraform 루트 모듈이 몇 개나 있고 태깅 상태가 어떤지부터 감사

- `provider.tf`에 alias(작업 유형별로 나눈 provider 별칭, 예: iam/network/compute)가 여러 개
- `default_tags`(provider 블록에 한 번 정의해두면 그 provider로 만들어지는 모든 리소스에 자동으로 병합되는 태그)를 쓰는 곳도 있고 안 쓰는 곳도 있음

코드에서 직접 스캔해서 표로 만들어보니 12개 루트 모듈 중 두 곳에 태깅 체계가 아예 없음을 확인

태그 키는 세 개로 결정

- **`Project`** — 서비스명
- **`ReleaseEnv`** — 배포 환경
- **`CostCategory`** — 리소스 유형

파이프라인 배포용 IAM Role만 모아둔 `shared` 루트 모듈들은 애초에 `Product`/`Stage` 같은 배포 환경 개념이 없는 리소스라 `ReleaseEnv`는 의도적으로 제외
과금 대상이 아닌 리소스라 태그를 붙여도 비용 분해엔 도움이 안 되고 권한만 추가로 필요해지는 걸 확인하고 최종 제외 (IAM 포함)

전략만 세워두고 끝낼 수도 있었지만, 실제로 적용해보지 않으면 권한 문제 같은 건 절대 드러나지 않을 것으로 판단해 바로 구현 착수

---

## 구현

가장 많이 쓴 패턴은 provider의 `default_tags`에 `Project`/`ReleaseEnv`를 고정값으로 넣고, `CostCategory`는 alias별로 다르게(`merge()` 함수로 병합) 넣는 방식
이 패턴을 아래 순서로 확산

1. 태그 키 오타(공유 인프라 루트 모듈) 수정
2. `default_tags`가 없던 루트 모듈 다섯 곳에 새로 적용
3. 리소스 레벨에서 provider 기본값과 어긋나 있던 값 정정
4. 태깅 체계가 아예 없던 루트 모듈 두 곳(GPU 인스턴스 관리, Terraform state 백엔드) 중 GPU 쪽만 우선 신설
5. CI 파이프라인 적용(apply) 중 드러난 권한 공백을 서비스별로 메움

값이 어긋나 있던 항목은 아래와 같음

| 문제 | 위치 |
|---|---|
| 환경 값이 `Product`가 아니라 `Production` | 서비스 C·D 여러 곳 |
| 환경 값이 소문자 `product` | 서비스 B 한 곳 |
| 같은 시크릿 저장소인데 유형 분류(`CostCategory`)가 서비스마다 다름 | 서비스 A·B |

권한 공백은 CI 파이프라인 역할이 그동안 특정 provider로 태그를 써본 적이 아예 없어서 생긴 것으로, 시크릿 저장소·알람·컨테이너 이미지 저장소·캐시·암호화 키·데이터베이스·로그 버킷·로드밸런서 순으로 apply를 반복하며 하나씩 찾아 추가
나중엔 에러 난 것만 쫓지 않고, 코드를 미리 훑어서 같은 이유로 곧 막힐 곳까지 한 번에 정리하는 방식으로 전환

작업 중 곁가지로 아래도 같이 처리

- **오타 수정** — 배포 전용 IAM Role 권한 설정에 한글 오타 섞여 저장 실패하던 문제 해결
- **드리프트 반영** — 서비스 C 로드밸런서 액세스 로그 설정(콘솔에만 존재)을 코드에 반영 (미반영 시 apply로 로그 수집 꺼질 뻔함)
- **죽은 코드 정리** — 대체되고 남은 주석 처리 코드 3곳 제거

## 결과

| 항목 | 작업 전 | 작업 후 |
|---|---|---|
| 태깅 체계 없는 루트 모듈 | 2곳 | Terraform state 백엔드 1곳(별도 작업 예정) |
| 값 불일치 | 6곳 | 0곳 |
| 태그 붙은 리소스 | 루트 모듈별 제각각 | 300개 이상 일관 적용 |
| 배포 파이프라인 권한 공백 | 다수(미확인 상태) | 서비스별로 메움 |

리소스 재생성 없이 태그만 갈아끼우는 변경이라 서비스 영향 없음
배포 파이프라인 권한 정책도 같이 정비됐는데, 정리하다 보니 정책 안에 중복되거나 이름이 실체와 안 맞는 구문들도 발견돼 별도 정리 후보로 등록

## 회고

전략을 먼저 문서로 정리하고 시작한 게 도움이 됨
태그 키를 뭘로 할지, 어떤 루트 모듈은 특정 키를 빼야 하는지 같은 판단을 미리 해두니 실제 구현 단계에서 헤매지 않음

반대로 권한 문제는 미리 예측하기 어려웠음
코드는 다 맞는데 apply할 때마다 새로운 서비스에서 권한이 막히는 걸 반복하다 보니, 나중엔 에러가 난 것만 고치지 않고 아직 안 걸린 것까지 미리 찾아 한 번에 처리하는 방식으로 전환
이렇게 안 했으면 apply-실패-권한추가를 훨씬 더 여러 번 반복했을 것으로 추정

아쉬운 점은 배포 파이프라인 권한 정책이 계속 땜질식으로 커지고 있다는 걸 이번에 확인한 것
언제 왜 추가됐는지 기록이 없는 광범위한 권한(계정 내 모든 S3 버킷을 읽을 수 있는 권한 등)도 발견했는데, 지금 당장 코드가 그걸 쓰는 것 같진 않지만 왜 열려 있는지는 확인 불가
다음에 시간 내서 이 정책 자체를 한 번 정리할 필요

다음에 할 일은 Terraform state 백엔드 루트 모듈의 태깅을 별도로 마무리하는 것과, AWS Billing 콘솔에서 이번에 쓴 태그 키들을 Cost Allocation Tags로 활성화하는 것
코드 작업은 여기까지고, 활성화 이후에 실제로 Cost Explorer에서 원하던 대로 분해가 되는지 확인하면 이번 작업은 완전히 종료
