## 배경

[[00-비용 태깅 정리]]에서 태그 키 세 개(`Project`, `ReleaseEnv`, `CostCategory`)를 쓰기로 결정했으니 이제 실제로 코드에 적용할 차례
전략을 세우면서 이미 코드베이스를 훑어봤는데, 공유 인프라 루트 모듈 하나에 태그 키 오타가 있었고 몇몇 루트 모듈은 `default_tags`(provider 블록에 한 번 정의하면 그 provider로 만든 모든 리소스에 자동으로 태그가 병합되는 Terraform AWS provider 기능)가 아예 없음을 확인

## 접근

제일 작고 안전한 것부터 처리하기로 결정
태그 키 오타 하나 고치는 건 리소스를 새로 만들거나 지우는 게 아니라 태그 값만 바뀌는 in-place 변경이라 리스크가 거의 없음
배포 파이프라인 전용 IAM Role만 모아둔 루트 모듈들은 `Product`/`Stage` 같은 배포 환경 개념 자체가 없는 리소스들이라 `ReleaseEnv` 키를 넣는 게 맞는지부터 확인 필요
이 루트 모듈들이 실제로 뭘 관리하는지(파이프라인용 IAM Role, 거기 붙는 정책, 정책 목록을 강제하는 리소스뿐이라는 것) 코드를 먼저 훑어보고 `ReleaseEnv`는 빼고 `Project`/`CostCategory`만 넣기로 결정

---

## 구현

변경한 곳은 아래 여섯 루트 모듈

| 루트 모듈 | 변경 내용 |
|---|---|
| 공유 인프라 | 컨테이너 클러스터 정의의 `ReleaseEnv` 오타(`RelaseEnv`) 두 곳 수정 |
| 서비스 B 메인 | `default_tags` 신규 적용 (`Project`/`ReleaseEnv`/`CostCategory` 전부) |
| 서비스 A 파이프라인 | `default_tags` 신규 적용 (`Project`/`CostCategory`만) |
| 서비스 B 파이프라인 | 〃 |
| 서비스 C 파이프라인 | 〃 |
| 서비스 D 파이프라인 | 〃 |

서비스 B 메인 루트 모듈은 이미 다른 서비스들이 쓰던 것과 같은 패턴(provider alias별로 세 태그를 자동으로 붙이는 방식)을 그대로 적용, 파이프라인 전용 루트 모듈 네 곳은 앞서 정한 대로 `ReleaseEnv`를 제외

적용 후엔 각 루트 모듈에서 `terraform plan`을 돌려서 태그만 바뀌고 리소스가 새로 생기거나 지워지지 않는지 하나하나 확인

## 결과

여섯 루트 모듈 모두 plan 결과가 "태그만 변경, 생성·삭제 없음"으로 확인

- 컨테이너 클러스터 2개 — 태그 키만 정정
- IAM Role 5개 루트 모듈 — 새 태그 추가
