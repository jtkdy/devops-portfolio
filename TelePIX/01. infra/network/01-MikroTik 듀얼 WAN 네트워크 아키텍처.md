## 배경

[[01-MikroTik-Suricata-Wazuh 온프렘 IDS 구축|Suricata IDS를 온프렘에 구축]]하기 전에, 정작 그 트래픽이 흘러가는 네트워크 장비(MikroTik RB4011) 자체의 구성을 문서로 남긴 사람이 없음
듀얼 WAN에 VLAN이 여러 개 나뉘어 있고 정책 기반 라우팅(PBR)까지 걸려 있는 상태라, "어느 인터페이스를 미러링해야 실제 위협 트래픽을 잡을 수 있는지"조차 라우터 설정을 직접 까보지 않고는 확인 불가
IDS를 제대로 설계하려면 먼저 이 네트워크가 실제로 어떻게 트래픽을 흘려보내는지부터 정리 필요

## 접근

라우터 설정을 그대로 옮겨적는 대신, "트래픽이 실제로 어느 인터페이스로 나가는가"를 기준으로 재구성
듀얼 WAN 환경에서는 방화벽 룰과 라우팅 룰이 따로 노는 경우가 많아서, 문서만 봐서는 "이 트래픽이 WAN1로 나가는지 WAN2로 나가는지" 확신 불가
그래서 각 VLAN에서 나가는 트래픽이 PBR 규칙을 거쳐 최종적으로 어느 WAN 인터페이스로 빠지는지 표로 명시적으로 정리하는 방식을 채택

방화벽 룰을 훑는 과정에서 설정 자체의 문제도 몇 개 발견
존재하지 않는 인터페이스를 참조하는 무효 룰, 코멘트에 적힌 IP와 실제 매치 조건 IP가 서로 다른 룰 등, 오랫동안 운영되면서 정리되지 않은 흔적들
이런 건 발견 즉시 고치기보다, IDS 구축이라는 원래 목적에 집중하기 위해 우선 목록화만 해두고 넘어감

## 구현

### 듀얼 WAN 정책 기반 라우팅(PBR)

VLAN10(AI/R&D)과 VLAN20(서버망)에서 나가는 신규 연결은 기본적으로 WAN2로 분산되도록 라우팅마크가 걸려있고, 내부망·VPN·파트너사 S2S(Site-to-Site) 대역으로 가는 트래픽만 예외적으로 WAN1(메인 라우팅)을 그대로 탄다

| 출발 VLAN | 인터넷행 트래픽 | 내부/VPN/S2S 트래픽 |
|---|---|---|
| VLAN10 (AI/R&D) | WAN2 | WAN1 |
| VLAN20 (서버망) | WAN2 | WAN1 |
| VLAN30/40/기타 | WAN1(기본) | WAN1 |

이 표가 IDS 설계에 결정적
서버망(VLAN20, 보안 모니터링 서버 포함)의 외부 통신이 주로 WAN2에서 관측된다는 뜻이라, TZSP 미러링 대상을 WAN1+WAN2 둘 다로 잡아야 한다는 근거로 확정

### VLAN 세그먼트

| VLAN | 용도 |
|---|---|
| 10 | AI/R&D GPU 워크스테이션망 |
| 20 | 서버망 (보안 모니터링 서버, 외부 노출 서버 등) |
| 30 | Office |
| 40 | 기타 설비 연동 |
| 99 | 관리(스위치 디스커버리 임시) |

### VPN 구성

- **개인 원격접속(WireGuard)** — 사설 대역 하나에 약 20개 피어(/32 할당) 등록, 그 중 하나는 [[02-WireGuard 터널로 EC2-온프렘 SSH 접근 구성|EC2→온프렘 SSH 접근용 피어]]
- **외부 파트너사 S2S(Site-to-Site)** — 금융권 파트너사와 IPsec 기반 사이트 간 VPN, 특정 대역만 양방향 forward 허용

### 방화벽 점검에서 발견한 정리 대상

- 존재하지 않는 인터페이스를 참조하는 무효 룰 2건
- 비활성화된 디버그 룰 2건
- 코멘트에 적힌 IP와 실제 매치 조건 IP가 서로 다른 룰 4건 — 이 중 하나는 **크립토재킹 사고의 공격자 IP를 여전히 WireGuard/IPsec 허용 룰에 남겨두고 있었다** ([[홈페이지 임시서버 크립토재킹 사고|관련 인시던트]])

### 시간대 불일치

라우터는 KST(Asia/Seoul)를 쓰는데 Suricata가 설치될 서버는 UTC를 쓰고 있어서, 나중에 두 시스템의 로그를 시간 기준으로 상관분석하려면 9시간 차이를 보정해야 한다는 걸 미리 확인

## 결과

- IDS 미러링 대상을 WAN1+WAN2 양방향으로 잡을 근거를 PBR 분석으로 확정, 실제로 이 결정이 [[01-MikroTik-Suricata-Wazuh 온프렘 IDS 구축|Suricata 구축]]에 그대로 반영
- VLAN/DHCP/NAT/방화벽 구성 전체를 문서 하나로 정리, 이후 신규 서버 추가나 트러블슈팅 시 참고 가능한 기준 문서 확보
- 방화벽 룰 정리 대상(무효 룰, 코멘트 불일치, 공격자 IP 잔존 룰)을 별도 TODO로 목록화

## 회고

네트워크 장비 설정은 한번 잡아두면 잘 안 건드리게 되는데, 그러다 보니 시간이 지나면서 무효 규칙이나 의미를 알 수 없는 예외가 쌓인다는 걸 이번에 직접 확인
특히 공격자 IP가 방화벽 룰에 여전히 남아있었던 건, 사고 대응 당시 서버 레벨(패스워드 변경, 보안그룹)만 조치하고 네트워크 장비까지는 점검하지 못했다는 뜻이라 뼈아픈 지점
사고 대응 체크리스트에 "네트워크 장비 방화벽 룰도 같이 확인"을 항목으로 추가할 필요

PBR 같은 정책 기반 라우팅은 방화벽 룰만 봐서는 실제 트래픽 흐름을 알 수 없다는 것도 다시 확인
"이 트래픽이 어디로 나가는가"를 표로 명시적으로 재구성하는 작업이 번거로웠지만, 그 표가 없었다면 IDS 미러링 대상을 잘못 잡았을 가능성
