## 배경

비용 최적화 점검 중에 ElastiCache 클러스터 2개 발견
하나는 실제로 쓰이는 게 확실했지만, 다른 하나(`telepix-redis-001`)는 용도를 아는 사람이 아무도 없음
둘 다 월 비용 발생 중(합계 약 $162/월), 쓰지도 않는 리소스에 계속 돈을 내고 있을 가능성이 있어 실사용 여부부터 확인하기로 함

## 접근

실제로 서비스가 물려있는데 착각해서 지우면 장애로 직결되기 때문에, 지우기 전에 여러 각도에서 교차 검증하는 절차 수립

- **CloudWatch 지표** — 연결 수·명령어 실행 수 확인
- **ECS 태스크 정의** — 환경변수에서 리소스 참조 여부 확인
- **Secrets Manager/SSM Parameter Store** — 관련 항목 등록 여부 확인
- **담당자 확인** — 용도 파악 가능 여부 확인

이 네 가지가 전부 겹쳐야 "미사용"이라고 결론 내릴 수 있다고 판단

- **함정** — `terraform-cache`는 `CurrCommands`(명령어 실행 수) 지표가 0으로 나와 미사용처럼 보였지만, 실제로는 LLM 응답 스트리밍에 `XREAD BLOCK`(블로킹 대기) 방식을 써서 명령어가 실행되고 있어도 카운트에 안 잡히는 구조
- **교훈** — 반드시 ECS 태스크 정의 레퍼런스까지 같이 확인 필요

## 구현

### 조사 결과

- **CloudWatch 지표** — `telepix-redis-001`: `CurrConnections` 5개 고정(변동 없음), `CurrCommands` 7일간 0
- **연결 주체 추적** — SG 인바운드 규칙은 등록돼 있었지만 실제 연결 여부와 무관, ECS 태스크 정의 환경변수 참조 없음, Secrets Manager/SSM Parameter Store 관련 항목 없음, 담당자도 용도 파악 불가
- **`terraform-cache` 반대 사례** — `CurrCommands` 0이지만 실제 태스크 정의에서 참조 확인, `XREAD BLOCK` 구조 때문에 지표에 안 잡히는 것으로 판명

### 삭제 절차

1. 사내 Slack 공지로 사용 여부 확인 요청, 회신 기한 명시 → 회신 없음 확인
2. 자동 스냅샷을 수동 스냅샷으로 복사 (영구 보관, 자동 스냅샷은 삭제 시 같이 소멸)
3. 클러스터 삭제

### 보안 점검에서 같이 발견한 것

- `terraform-cache` — AuthToken 미설정, 전송/저장 암호화 둘 다 미적용, 백업 보관 0개, CSAP 통제 항목 위반
- `telepix-redis-001`(삭제 전 기준) — 저장 암호화는 적용돼 있었지만 전송 암호화가 `preferred`(선택)로만 설정, AuthToken 미설정

## 결과

- `telepix-redis-001` 삭제 완료, 월 ~$17.5 절감
- 실사용 중인 `terraform-cache`는 암호화·인증 미적용 상태로 계속 운영 중이라는 리스크가 남음 — 다만 in-place로는 암호화 적용이 안 돼서 클러스터 재생성이 필요하고, 이건 트래픽 최저 시간대를 잡아 애플리케이션 TLS/AUTH 코드까지 같이 반영해야 하는 별도 작업으로 분리

## 회고

`CurrCommands` 지표 하나만 보고 판단했으면 실제로 쓰이는 캐시를 지울 뻔했음
모니터링 지표는 애플리케이션이 그 지표를 발생시키는 방식(polling vs blocking)에 따라 실제 사용량을 제대로 반영을 못 할 수 있어 그 이후로는 리소스 삭제 판단에 지표 단독 근거를 쓰지 않고, 반드시 코드/설정 레퍼런스까지 교차 확인 필요

암호화 안 된 채로 계속 운영 중인 `terraform-cache`는 여전히 남은 숙제
안 쓰는 걸 지우는 것보다 쓰고 있는 걸 안전하게 만드는 쪽이 더 손이 많이 가고 다운타임을 감수해야 해서 우선순위가 밀려있는데, 이런 식으로 "위험하지만 손대기 번거로운" 항목이 계속 뒤로 밀리지 않도록 별도로 추적 필요
