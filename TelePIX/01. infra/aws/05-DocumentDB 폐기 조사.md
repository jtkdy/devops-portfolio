## 배경

비용 최적화 점검을 이어가다가 DocumentDB 클러스터 2개 발견
둘 다 태그가 하나도 없어서 누가 왜 만들었는지 이름만 봐서는 알 수 없었고, 인스턴스 스펙(db.t3.medium)만 봐도 월 130달러 가까이 나가는 상태
삭제해도 되는지 판단하려면 실제로 데이터가 들어있는지, 지금 서비스가 이걸 쓰고 있는지부터 확인 필요

## 접근

하나는 Terraform state가 아예 없었고(콘솔에서 수동 생성된 것으로 추정), 다른 하나도 state가 없는 채로 드리프트된 상태
관리 주체가 불분명한 리소스라 더 신중하게 접근할 필요
[[04-Redis 클러스터 폐기 조사|Redis 건]]에서 배운 대로 지표 하나로 판단하지 않고, 연결 지표·CloudTrail 접근 이력·현재 서비스의 실제 연결 여부를 전부 겹쳐서 확인하기로 함

bastion을 경유해서 `mongosh`로 직접 접속해 내부 데이터를 확인
이 방법으로 "그냥 비어있는 DB"인지 "예전에 쓰다가 방치된 DB"인지까지 구분 가능

## 구현

### 조사 결과

- **연결 수** — 두 클러스터 모두 최근 7일 `DatabaseConnections` 최대값 0
- **CloudTrail** — 최근 90일간 접근 이벤트 없음
- **운영 서비스 연결 여부** — 현재 서비스 태스크 정의에 MongoDB/DocumentDB 관련 환경변수 없음, PostgreSQL(pgvector/PostGIS) 기반으로 이미 전환 완료된 상태 확인
- **내부 데이터 직접 확인** (TLS 비활성 클러스터) — bastion 경유 `mongosh` 접속, DB 4개 모두 최소 7개월 이상 활동 없는 잔존 데이터로 확인, 그 중 하나는 문서 0건인 빈 DB
- **나머지 클러스터** — 비밀번호 미확인으로 내부 데이터 조회는 못 했지만, 보안그룹이 NAT 인스턴스 전체 대역을 허용하고 있어 특정 서비스를 위한 것이라기보다 방치된 설정에 가깝다고 판단

### 보안 이슈

- TLS 비활성 + 암호화 미적용 클러스터 1개
- 보안그룹이 특정 서비스가 아니라 NAT 인스턴스 대역 전체를 허용
- 두 클러스터 모두 태그 없음 — 소유자/목적 추적 불가

### 삭제 절차

1. 개발팀에 Slack으로 사용 여부 확인 요청 → 회신 수신, 데이터 불필요 확인
2. Final 스냅샷 생성
3. 인스턴스 삭제 → 클러스터 삭제
4. Terraform state 없는 리소스라 별도 state 정리 불필요

## 결과

- 클러스터 2개 삭제 완료, 월 ~$130 절감
- 관련 보안그룹도 함께 정리 권장 사항으로 남김
- 스냅샷은 30일 보존 후 삭제 예정으로 별도 추적

## 회고

두 클러스터 다 태그가 없어 소유자나 목적을 리소스 자체에서 알 수 없으니 CloudWatch, CloudTrail, 코드, 사람에게 직접 묻는 것까지 전부 동원 필요
이 경험 이후로 신규 리소스 생성 시 태그를 필수로 강제하는 게 왜 중요한지 체감 — 나중에 이걸 지워도 되는지 판단하는 데 드는 시간이 태그 하나 붙이는 것보다 훨씬 큼

지표나 로그만으로는 "정말 안 쓰는 데이터인지" 확신하기 어려웠는데, 실제 데이터를 열어보고 나서야 "서비스 전환 전 잔존 데이터"라는 확신이 생김
다만 이 방식이 통했던 건 TLS가 꺼져 있어서였고, 정상적으로 암호화된 DB였다면 비밀번호부터 확보해야 하는 문제라 이번처럼 쉽게 확인하지 못했을 것으로 예상
