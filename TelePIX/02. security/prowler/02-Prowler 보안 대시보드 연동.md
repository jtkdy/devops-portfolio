## 배경

[[01-Prowler Self-Hosted 구축|Prowler를 Self-Hosted로 EC2에 구축]]해서 매일 계정 전체를 스캔하도록 운영하기 시작했는데, 문제는 이 결과를 확인하려면 Prowler 전용 콘솔에 따로 접속해야 했다는 점
사내 개발자 포탈에는 이미 저장소 취약점 스캔, ACM 인증서, S3 보안 감사 등을 모아 보여주는 보안 탭이 있었기 때문에, Prowler 결과도 이 탭 안에 자연스럽게 편입시키면 별도 로그인 없이 한 화면에서 인프라 보안 현황을 볼 수 있겠다고 판단

## 접근

가장 먼저 정한 건 포탈 백엔드가 Prowler API를 어떻게 부를 것인가
별도 프록시나 게이트웨이를 새로 두는 방안도 잠깐 고려했지만, 포탈은 이미 형상관리 API나 OSV(오픈소스 취약점 DB) API처럼 외부 API를 백엔드에서 직접 호출하는 패턴을 여러 곳에서 사용 중
굳이 새 아키텍처를 들일 이유가 없어, 포탈 서버가 Prowler API를 직접 호출하는 가장 단순한 방식으로 결정

인증 크레덴셜 저장 방식도 고민 대상
Prowler API가 JWT 토큰 발급을 요구하는데, 이 발급용 계정 정보를 어디에 둘지가 문제
포탈은 다른 외부 서비스 토큰과 시크릿을 전부 환경변수 한 줄로 통일해서 관리하고 있고 별도 Secrets Manager는 쓰지 않는 프로젝트
Prowler 계정 정보만 예외로 둘 이유가 없어 이 패턴을 그대로 따르기로 결정

캐시 전략은 기존 취약점 스캔 기능과 살짝 다르게 가져감
기존 취약점 스캐너는 결과를 인메모리에만 들고 있다가 재기동하면 날아가는 구조인데, Prowler는 계정 하나에 FAIL 상태 findings가 천 건 넘게 쌓여있는 규모라 재기동 직후에도 최근 결과를 바로 보여주고 싶었음
그래서 포탈의 기존 Store 패턴(JSON 파일 영속화)을 그대로 가져와 캐시를 파일로 저장하기로 결정

## 구현

### 네트워크와 인증

- **API 포트 개방** — Prowler EC2 보안그룹에 UI 포트만 열려있고 API 포트는 인바운드 자체가 부재, 포탈 서버 보안그룹을 소스로 지정해 추가
- **400 차단 (ALLOWED_HOSTS)** — 포트 개방 후에도 API 호출이 계속 400
  - 원인: Django `ALLOWED_HOSTS`가 `localhost`/`127.0.0.1`/컨테이너 내부 서비스명만 허용, 포탈 서버가 사설 IP로 요청하면 Host 헤더 검증에서 거부
  - 해결: Prowler EC2 환경설정 파일에 포탈 서버·Prowler 자신의 사설 IP를 허용 목록에 추가하고 API 컨테이너 재기동
- **JWT 인증** — JSON:API 포맷 로그인으로 access 토큰 발급, 클라이언트 모듈에서 메모리 캐싱 + `exp` 클레임 디코드해 만료 60초 전 자동 재로그인, 401 응답 시 1회 재로그인 후 재시도, 토큰·비밀번호는 로그·예외 메시지에 원문 미기록
- **`GET /findings` 스펙 이슈** — 날짜 필터 미지정 시 400, 조회 범위 7일 초과 시 에러
  - 해결: 갱신 시각 기준 6일 전부터 조회 — 매일 도는 스캔 특성상 이 범위로도 최신 결과 누락 없음

### 캐시와 API

- **캐시 스케줄러** — 요약(severity별 카운트)·findings 최근 200건·스캔 이력을 1시간 주기로 JSON 파일 캐시에 갱신
- **실시간 우선 + 캐시 폴백**
  - 기본 동작 — 노출 API 세 개(요약/findings/스캔 이력) 모두 매 요청마다 Prowler API 실시간 호출을 우선, 무응답 시에만 캐시로 폴백
  - findings — 건수가 많아 페이지네이션·필터를 Prowler API에 그대로 위임, 캐시는 장애 시 축소 경로로만 사용
- **API 권한 구멍 발견** — 기존 인증 미들웨어만 걸었더니 사이드바 메뉴는 숨겨도 API 직접 호출은 뚫려있는 상태 확인
  - 원인: 기존 ACM/S3/취약점 API도 같은 구조지만, 홈 화면 요약 위젯이 전체 로그인 사용자 대상으로 그 API들을 쓰고 있어 막을 수 없는 상황
  - 해결: Prowler API는 대시보드 화면 전용이라 다른 의존처가 없음을 확인, 이 라우터에만 서버 사이드로 상위 권한 role 체크 추가

### 화면

프론트엔드는 기존 취약점 스캔 화면과 같은 톤으로 제작, 요약 카드에 severity별 건수 표시, Prowler API 무응답 시 캐시 대체 상태를 경고 배지로 표출
findings 테이블에 severity 필터·페이지네이션 부착 후 실사용하며 몇 가지 손볼 점 확인

- **컬럼 너비 드래그 조절** — Check ID/리소스명 잘림 해결, 전체 폭 고정 + 인접 컬럼끼리만 폭 주고받는 방식, `localStorage`에 저장해 새로고침 후에도 유지
- **페이지네이션 개선** — 이전/다음 버튼 → 화살표 아이콘 + 페이지 번호 목록(현재 페이지 앞뒤 일부, 나머지 생략부호) 형태로 변경

## 결과

- 보안 탭에서 Prowler 스캔 결과(critical/high/medium/low 건수, FAIL findings 상세, 스캔 이력)를 별도 로그인 없이 바로 확인 가능
- Prowler API가 일시적으로 응답하지 않아도 캐시된 최근 결과로 화면이 비지 않음
- 실제 운영 서버에 배포한 뒤 세 API 모두 실시간 데이터로 정상 응답하는 것 확인

## 회고

이번 작업에서 가장 시간이 많이 든 부분은 코드 자체보다 Prowler API의 실제 동작을 하나씩 확인하는 과정
OpenAPI 스키마만 보고는 날짜 필터가 필수인지, 범위 제한이 있는지 전혀 파악 불가했고, `ALLOWED_HOSTS` 문제도 에러 메시지만 봐서는 원인 짐작이 어려웠음
로컬 개발 환경에서는 애초에 Prowler EC2(사설 IP)에 접근이 안 된다는 걸 뒤늦게 깨닫고 잠시 헤맨 것도 아쉬운 점
사내망 전용 리소스를 다루는 기능은 처음부터 "로컬에서는 검증 불가능하고 실 서버 배포 후에만 확인 가능하다"는 걸 전제로 작업 순서를 짰으면 더 매끄러웠을 것

반대로 잘된 점은, 기존 ACM/S3/취약점 API가 갖고 있던 "화면은 숨겨도 API는 열려있다"는 잠재적 구멍을 이번에 Prowler를 붙이면서 같이 발견하고, 최소한 이번 신규 기능에는 서버 사이드 role 체크를 제대로 넣었다는 점
다만 기존 3개 API는 홈 위젯 때문에 그대로 열어둘 수밖에 없었는데, 이후 홈 위젯이 필요로 하는 데이터만 골라내는 요약 전용 엔드포인트를 따로 만들고 상세 API는 role로 잠그는 식으로 정리할 계획
