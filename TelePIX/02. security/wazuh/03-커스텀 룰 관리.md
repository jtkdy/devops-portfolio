## 배경

FIM 노이즈는 syscheck 설정으로 줄였는데, 데일리 리포트에는 여전히 의미 없는 alert들이 혼재
Docker `veth` 인터페이스가 컨테이너 생성/삭제 때마다 promiscuous mode에 진입하면서 level 8 alert를 2,700건 넘게 발생시키고 있었고, 이미 패치된 패키지를 취약점으로 잘못 감지하는 CVE false positive도 누적

Wazuh 기본 룰셋을 건드리지 않고 `local_rules.xml`에서 환경에 맞게 덮어쓰거나 억제하는 방식으로 관리 결정
억제 룰을 추가하기 전에는 반드시 정상 동작임을 팩트로 확인해야 한다는 원칙 수립 — 확인 없이 억제하면 실제 위협을 놓칠 수 있기 때문

## 접근

Wazuh는 `local_rules.xml`에서 기본 룰을 오버라이드하거나 새 룰을 추가 가능
level을 0으로 설정하면 해당 이벤트가 완전히 억제
크게 두 가지 목적으로 사용

- **노이즈 억제** — 정상 동작임이 확인된 이벤트의 level을 낮추거나 0으로 억제, Docker `veth` promiscuous mode나 Agent buffer full alert가 여기에 해당
- **CVE false positive 처리** — Wazuh vulnerability detection이 이미 패치된 패키지를 Active 취약점으로 잘못 감지하는 경우 존재, `apt-cache policy`로 `Installed == Candidate`를 확인한 뒤 최신 패치가 적용된 것으로 판단되면 해당 CVE만 억제

## 구현

파일을 수정한 뒤 Manager를 재시작하면 적용

```bash
docker restart single-node-wazuh.manager-1
docker exec single-node-wazuh.manager-1 \
  grep -A4 "rule id" /var/ossec/etc/rules/local_rules.xml
```

### 100001~100003 — dpkg 이벤트 level 낮춤

dpkg 패키지 설치/제거/반설정 이벤트는 기본적으로 높은 level로 잡히는데, 개발 서버에서는 일상적인 작업이라 level 3(informational)으로 하향


```xml
<group name="local,dpkg">
  <rule id="100001" level="3" overwrite="yes">
    <if_sid>2902</if_sid>
    <description>New dpkg package installed (informational)</description>
  </rule>
</group>
```

### 100010 — Docker veth promiscuous mode 억제

Docker 컨테이너 서버에서 하루 2,725건 발생하던 level 8 alert
`veth*` 인터페이스는 Docker 컨테이너 생성/삭제 시 자동으로 만들어지고 사라지는 가상 인터페이스로, promiscuous mode 진입은 Docker 브릿지 네트워킹의 정상 동작
`veth` 매칭 조건을 걸었기 때문에 실제 물리 인터페이스(`eth0`, `ens*` 등)의 promiscuous mode는 여전히 탐지 유지

```xml
<group name="local,syslog,kernel">
  <rule id="100010" level="0" overwrite="no">
    <if_sid>5104</if_sid>
    <match>veth</match>
    <description>Docker veth interface promiscuous mode change (ignored)</description>
  </rule>
</group>
```

### 100011 — Agent buffer full alert 억제

이미지 처리 서버의 rootcheck 스캔 시작 시 순간적으로 이벤트가 폭주해 버퍼가 꽉 차는 현상 발생
`events_per_second` 500 → 250 조정([[01-에이전트 설치 및 구성]] 참고)으로 근본 조치 완료, alert도 함께 억제

```xml
<group name="local,agent_flooding">
  <rule id="100011" level="0" overwrite="no">
    <if_sid>203</if_sid>
    <description>Agent event queue full (suppressed - eps tuned)</description>
  </rule>
</group>
```

### 100020~100026 — CVE False Positive 억제

false positive 확인 절차는 간단
`apt-cache policy <패키지명>`을 실행해서 `Installed`와 `Candidate` 버전이 같으면 이미 최신 패치가 적용된 상태

| Rule ID | CVE | 패키지 |
|---|---|---|
| 100020 | CVE-2020-24372 | libluajit-5.1-2, libluajit-5.1-common |
| 100021~100023 | CVE-2026-59856~59858 | vim, vim-common, vim-runtime, vim-tiny, xxd |
| 100024 | CVE-2026-33164 | libde265-0 |
| 100025 | CVE-2024-5138 | snapd |
| 100026 | CVE-2026-26740 | libgif7 |

```xml
<group name="local,vulnerability">
  <rule id="100020" level="0" overwrite="no">
    <if_sid>23505</if_sid>
    <match>CVE-2020-24372</match>
    <description>CVE-2020-24372 false positive - package already patched</description>
  </rule>
</group>
```

새로운 CVE false positive 확인 시 100027부터 순차 추가하고, 억제 전 반드시 패치 적용 여부를 먼저 확인하도록 규칙 수립

### 룰 ID 체계

| 범위 | 용도 |
|---|---|
| 100001 ~ 100009 | dpkg/패키지 관련 |
| 100010 ~ 100019 | Docker/컨테이너 관련 |
| 100020 ~ 100029 | CVE false positive 억제 |
| 100030 ~ | 추후 확장 |

## 결과

veth promiscuous mode 억제 후 데일리 리포트에서 High 건수가 2,725건에서 0건으로 감소
CVE false positive 억제 후 vulnerability 섹션에서 이미 알고 있는 항목들이 사라지고, 실제로 확인이 필요한 신규 CVE만 남음

## 회고

`veth` 매칭 조건을 사용해서 물리 인터페이스의 promiscuous mode는 살려둔 게 적절한 선택
억제하되 실제 위협 탐지는 유지하는 균형이 맞음

CVE false positive가 계속 누적 중
패키지 업데이트 후 Wazuh vulnerability database 갱신 시점이 맞지 않아 발생하는 구조적인 문제라 근본 해결은 어렵고, 운영하면서 계속 관리해야 하는 항목
룰이 100개 이상 쌓이면 관리가 어려워질 것 같아, 카테고리별로 파일을 분리하는 방안을 나중에 검토할 예정
