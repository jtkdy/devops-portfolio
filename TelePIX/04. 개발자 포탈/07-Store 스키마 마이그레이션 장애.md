## 배경

개발자 포탈은 DB 없이 JSON 파일 기반 Store로 데이터를 관리
서비스 카탈로그의 `links` 필드를 `{repo, monitoring, pipeline}` 형태의 dict에서 `[{label, url}]` 배열로 바꾸는 작업을 하면서, 프론트엔드가 새 배열 형태를 기대하도록 먼저 코드를 짜고 배포
이 과정에서 2026-07-31에 실제 장애 발생

## 접근

당시엔 스키마 변경을 "필드 타입만 바꾸는 작업"으로 가볍게 보고, 마이그레이션 스크립트는 로컬에서만 돌려서 확인한 뒤 프론트 코드를 먼저 배포
백엔드 운영 데이터(JSON 파일)는 그대로 두고 프론트만 새 코드로 나간 상태

## 구현 (사고 당시 상태)

- 프론트: `links.filter(...)` 등 배열 메서드를 호출하는 새 코드로 배포됨
- 백엔드/운영 데이터: `links`가 여전히 예전 dict 형태
- 결과: 프론트가 dict에 `.filter()`를 호출하면서 `TypeError` 발생 → React 전체가 죽어 흰 화면

## 결과 — 원인 분석과 재발 방지

원인을 추적하면서 두 가지가 겹쳐 있다는 걸 확인

1. 마이그레이션 스크립트를 로컬에만 돌리고 운영 데이터에는 실행하지 않음
2. 서비스 카탈로그 Store(다른 Store도 동일)는 `_load()`를 생성자에서 딱 한 번만 호출하는 구조라, 파일을 외부에서 직접 고쳐도 백엔드를 재시작하기 전까지 메모리엔 반영되지 않음, 이 상태에서 다른 서비스 하나라도 update되면 메모리에 있던 예전 데이터 전체가 파일에 그대로 다시 저장돼서, 나중에 마이그레이션을 돌려도 덮어써질 위험까지 존재

이 두 가지를 근거로 스키마를 바꿀 때 지켜야 할 순서를 체크리스트로 확정

1. 마이그레이션 스크립트 작성 (dry-run 지원 필수, 실행 전 자동 백업)
2. 운영 배포 전에 마이그레이션 스크립트를 운영 데이터에 먼저 실행 (dry-run으로 확인 후 실행)
3. 마이그레이션 직후 백엔드 컨테이너를 재시작해서 새 파일을 메모리로 다시 로드
4. 그 다음에 새 코드(프론트/백엔드)를 배포
5. 배포 후 `curl`로 실제 API 응답 타입을 확인해서 마이그레이션이 반영됐는지 검증

이 체크리스트는 내부 개발 가이드 문서에 문서화해서 이후 모든 Store 스키마 breaking change에 예외 없이 적용하도록 강제
이후 같은 유형(마이그레이션 순서 누락으로 인한 장애)의 사고는 재발 없음

## 회고

이 장애의 근본 원인은 "Store가 파일을 최초 1회만 로드한다"는, 코드에는 있지만 눈에 잘 안 띄는 제약을 스키마 변경 작업을 할 때 고려하지 않은 것
AI에게 "필드 타입 바꿔줘"라고 요청하면 필드를 다루는 코드는 정확히 고쳐주지만, "이 변경이 배포 순서에 어떤 영향을 주는가" 같은 시스템 전체 관점의 질문은 명시적으로 묻지 않으면 나오지 않는다는 걸 이 사고로 체감

이후로는 스키마를 바꾸는 작업을 시작하기 전에 "이 Store를 읽는 다른 프로세스/배포 시점은 몇 개인가"를 먼저 확인하는 습관 형성
아쉬운 점은 이 체크리스트가 사고를 겪은 뒤에야 만들어졌다는 것
다음에는 이런 리스크가 큰 변경 유형(스키마 변경, 시크릿 처리, 인증 경계)을 미리 목록화해서, 사고가 나기 전에 체크리스트를 세워두고 싶음
