## 배경

모니터링 알림 규칙은 있었지만, 알림이 뜨면 사람이 슬랙에 옮겨 적고 담당자를 태그하고 기록을 남기는 것까지는 전부 수동
알림은 자동인데 그 뒤는 사람 손이라는 게 이상해서, 그 흐름만 이어붙이면 되겠다 싶어 시작

## 접근

처음 그린 그림은 지금보다 훨씬 컸음
장애가 뜨면 봇 토큰으로 그 장애 전용 비공개 슬랙 채널을 새로 파고, 카탈로그에 등록된 담당자를 자동으로 초대하는 방식이었음
막상 붙이려니 봇 토큰이라는 자격 증명을 새로 관리해야 하고, 알림 하나 뜰 때마다 채널이 생기고 사람이 초대되는 부작용이 매번 발생한다는 게 걸림
결국 기존 슬랙 웹훅으로 "등록됐다" 메시지 한 줄 보내는 걸로 축소하고 채널 생성 코드는 전부 제거
담당자는 어차피 메시지에 영향받은 서비스 이름이 찍히니, 그걸 보고 카탈로그에서 확인하면 충분하다고 판단

이 웹훅의 실패 방식도 미리 결정
시크릿이 안 잡혀 있으면 그냥 통과시키는 배포 웹훅과 달리, 이건 걸리면 곧바로 슬랙에 알림이 나가는 부작용이 있어서 시크릿이 없으면 아예 요청을 거부(503)하도록 구성
설정 실수로 아무 값이나 들어와서 엉뚱한 장애가 등록되는 것보다는, 잠깐 안 되는 쪽이 낫다고 판단

## 구현

중복 등록은 별도 dedup 키를 새로 만들지 않고, "지금 진행 중인 장애 중에 영향 서비스 목록이 완전히 같은 게 있으면 그걸 그대로 쓴다"는 규칙 하나로 처리

해소는 사람이 직접 닫도록 설계
모니터링이 정상으로 돌아왔다는 신호도 다시 보내주지만 그걸로 자동으로 닫지는 않는데, 순간적으로 회복됐다가 다시 튀는 경우도 있어서 자동 종료는 오히려 신뢰를 깎을 수 있다고 판단

권한 설계도 실사용 확인하면서 손봄

- **등록·해소 권한 확대** — 처음엔 관리자만 가능했는데, 실제 대응하는 사람이 항상 관리자는 아니라서 운영 역할까지 확대
- **조치 기록 개방** — 대응에 손을 대는 사람이면 누구나 남길 수 있도록 개방
- **해소 처리자 서버 측 추출** — 요청 값으로 받지 않고 서버가 인증된 사용자에서 직접 추출, 배포 승인 쪽에서 클라이언트가 보낸 이름을 그대로 믿다가 감사 기록이 위조될 뻔했던 문제를 겪은 뒤라 처음부터 이렇게 설계

필드도 처음엔 등록·해소뿐이었는데, 실제로 대응해보니 원인·영향 범위·타임라인이 필요해져서 나중에 추가

## 결과

지금은 알림이 뜨면 장애가 자동으로 등록되고 슬랙으로 바로 알림 발송
캘린더로 이력을 돌아볼 수 있고 홈 화면에도 최근 장애 노출
채널 자동 생성을 걷어낸 덕분에 봇 토큰 같은 걸 따로 관리할 일도 없음

담당자 확인은 아직 사람이 카탈로그를 열어봐야 하는 수동 단계로 남음
자동화할 수도 있지만, 지금까지는 그 정도 번거로움이 채널 자동 생성의 복잡도보다는 낫다고 보고 보류

## 회고

처음 그림을 그대로 밀어붙이지 않은 게 잘한 선택
만들다 보면 이왕 하는 거 다 자동화하고 싶어지는데, 실제로 필요했던 건 사람이 놓치지 않는 것까지였지 채널까지 파줄 필요는 없었음

해소 처리자를 서버에서 강제로 뽑는 부분은 이번에 새로 깨달은 거라기보다 다른 데서 이미 한 번 겪은 문제를 그대로 옮겨온 것에 가까움
이 기능만의 이야기라기보다 이 포탈 전체에 걸쳐 있는 패턴
