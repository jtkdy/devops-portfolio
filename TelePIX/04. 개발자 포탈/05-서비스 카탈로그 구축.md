## 배경

운영 중인 ECS 서비스가 몇 개고, 각각 담당자가 누군지, 어떤 클러스터에서 도는지를 한눈에 보여주는 화면이 부재
필요할 때마다 AWS 콘솔을 뒤지거나 사람에게 물어봐야 했고, 신규 입사자가 팀이 어떤 서비스를 운영하는지 파악하는 데도 시간 소요
서비스 목록과 담당자 매핑을 데이터로 관리하는 카탈로그를 먼저 만들고, 그 위에 실시간 상태를 얹는 순서로 설계

## 접근

다른 저장소들과 마찬가지로 DB 없이 JSON 파일 기반 Store로 구성했고, 다른 Store를 직접 참조하지 않는 원칙도 그대로 유지
상태 대시보드가 실시간으로 AWS ECS API에서 서비스 상태를 조회해오는데, 이 결과를 카탈로그 데이터와 연결할 때도 Store끼리 참조하게 하지 않고 API 레벨에서 두 데이터를 조합하는 방식 채택
카탈로그와 상태 대시보드가 같은 서비스 식별자(`ecs_service_name`)를 키로 쓰기 때문에 이 조합이 자연스럽게 성립

## 구현

- **그룹 탭** — 제품군별 그룹(4개) 탭을 카탈로그·상태 대시보드에 동일 적용, 값은 자유 입력 대신 선택형으로 제한해 오탈자발 탭 불일치 방지
- **캐시 키 통합** — 카탈로그·상태 대시보드·홈 화면 3곳의 react-query 캐시 키(`['service-catalog']`) 단일화, 한 화면 갱신 시 나머지도 동기화, 화면별 중복 API 호출 제거
- **죽은 기능 제거** — 활성/비활성 토글: 실사용 필터링 로직 전무 확인 후 스키마·API·화면 전체에서 제거
- **AWS 동기화** — ECS API로 서비스 목록 조회 → 카탈로그 미등록 서비스만 자동 채움, 수동 등록 제거

카탈로그의 `links` 필드는 처음에 레포·모니터링·파이프라인 세 개 키를 고정으로 가진 dict 구조였는데, 나중에 임의 개수의 라벨-링크 쌍을 담을 수 있는 배열 구조로 변경
이 변경은 운영 데이터 마이그레이션과 배포 순서를 지키지 않아서 실제로 화면이 하얗게 나가는 장애로 이어졌는데, 그 이야기는 [[01-사내 개발자 포탈 구축]]에 별도 정리

## 결과

- **핵심 수치** — 제품군 그룹 4개 표준화(자유 입력→선택형), 카탈로그·상태 대시보드·홈 화면 3곳 캐시 키 통합으로 화면별 중복 API 호출 제거, 실사용 없는 활성/비활성 토글 필드 1개 제거

지금은 카탈로그가 서비스 목록·담당자·관련 링크의 단일 기준점 역할을 하고, 상태 대시보드가 그 위에서 실시간 상태를 보여주는 구조로 자리잡음
홈 화면 위젯도 같은 데이터를 그대로 재사용해서 별도로 유지보수할 화면이 늘어나지 않음

## 회고

"쓰지 않는 필드는 남겨두지 않는다"는 원칙을 이번에 확실히 체감
활성/비활성 토글처럼 만들 때는 필요해 보였지만 실제로는 아무 로직도 안 거는 필드가 하나 있는 것만으로도, 나중에 누군가는 이 필드가 진짜 뭘 하는지 다시 확인해야 하는 부담 발생
기능을 추가하는 것만큼 안 쓰는 걸 걷어내는 것도 계속 챙겨야 하는 일이라는 걸 재확인

캐시 키를 여러 화면에서 통일해두는 습관은 이번 카탈로그뿐 아니라 이후 장애 관리 기능에도 그대로 이어짐
처음부터 이 데이터를 다른 화면에서도 쓸 수 있을지 생각하고 캐시 키를 잡아두면, 나중에 화면이 늘어나도 API를 새로 만들 필요 없이 기존 키를 재사용할 수 있다는 걸 습득
