## 배경

- 홈페이지 임시 서버(10.9.x.x)에서 서비스가 짧게는 6초, 길게는 49초씩 네 차례나 다운되는 걸 확인
- 처음엔 애플리케이션 자체 오류로 의심했는데, 로그를 들여다보니 Monero(XMR) 코인을 채굴하는 크립토재킹 프로세스가 서버 자원을 채굴 프로세스가 메모리를 과다 점유하면서 OOM(Out of Memory) kill 발생

## 접근

증상만 봐서는 침투 경로를 알 수 없어서, 서버 로그를 시간순으로 전부 재구성하는 방식으로 접근
OOM kill 로그와 DNS 쿼리 로그, 컨테이너 프로세스 목록을 각각 따로 훑고 시간대를 맞춰 확인

## 구현

### 침투 경로 추정

- `/etc/ssh/sshd_config`에 `PasswordAuthentication yes` 설정됨
- 원래는 AWS key pair 기반 개인키 로그인 방식. 어느 시점에 패스워드 인증이 켜져 있었고 인스턴스 보안그룹도 22번 포트를 공인 IP 전체에 열어두고 있었음
- 공격자 IP에서 ubuntu 계정으로 패스워드 인증을 통해 침투한 것으로 추정

### 컨테이너 내 악성 프로세스

정상 서비스 프로세스(`next-server`)와 함께 악성 프로세스 3개가 동시 동작

- `./139u8fu6` — 악성 바이너리
- `./9rnjkubx47pe` — 채굴기
- `/home/nextjs/molmfpla/.mmahrrefbmdi --guard > /dev/null 2>&1 &` — 워치독

이 워치독이 문제를 더 키웠는데 컨테이너가 재시작될 때마다 워치독이 악성 코드를 함께 재실행시켰고, 컨테이너를 단순히 재기동하는 것만으로는 문제가 해결되지 않는 구조 확인
이미지 자체가 감염됐을 가능성까지 염두에 둬야했음

### 조치

- **Ubuntu 계정 패스워드 변경** (완료)
- **보안그룹 특정 IP 차단** (일부 완료) — 공격자 IP 차단, 22번 포트를 내부 사용자 IP 대역(10.1.x.0/24)으로 제한, SSM 전환 후 22번 포트 완전 차단 예정
- **Frontend 컨테이너 종료 및 이미지 재생성** (예정) — 워치독이 재실행 시 악성 프로세스 복원시키므로 재기동이 아닌 이미지 재빌드/재배포 필요

OS 패키지/설정 레벨의 하드닝과, SSH 접근 경로 자체를 막는 네트워크/인증 레벨의 통제가 필요하다고 판단

## 결과

- 즉시 조치(패스워드 변경, IP 차단)로 재침투 차단 — 컨테이너 이미지 재생성은 사고 시점 기준 예정 상태
- 서비스 다운타임 총 4회, 최대 49초 — 피해는 경미, 원인 규명(자원 고갈성 크립토재킹)에는 로그 전체 재구성 필요

## 회고

가장 문제는 SSH 패스워드 인증이 켜져 있었다는 사실을 아무도 몰라 원래 개인키 방식으로 설계됐던 접근 방식이 언제, 왜 패스워드 인증으로 바뀌었는지 이 장애에서는 끝내 확인 불가
접근 방식 자체를 사람이 실수로 바꿀 수 없는 구조(SSM, IAM 기반 인증)로 가져가야 한다는 결론을 냄

이 장애를 계기로 온프렘/AWS 전반의 탐지 공백도 재확인함
DNS 쿼리 폭주(1,024개 초과)라는 명백한 이상 징후가 있었는데도 그걸 실시간으로 감지할 체계가 전혀 없었고 워치독으로 컨테이너가 계속 재감염되는 걸 보면서,
컨테이너 런타임 레벨의 이상 프로세스 탐지(Falco 같은 도구)나 이미지 취약점 스캐닝도 필요하다고 판단했는데 이 부분은 아직 손대지 못한 채로 남음

나중에 [[01-MikroTik 듀얼 WAN 네트워크 아키텍처|온프렘 라우터 방화벽 룰을 점검]]하다가, 이 사고의 공격자 IP가 WireGuard/IPsec 허용 룰에 여전히 남아있는 걸 확인
사고 당시 조치가 서버 레벨(패스워드 변경, 보안그룹)에만 머물고 네트워크 장비까지는 못 미쳤다는 뜻이라, 이후 사고 대응 절차에 네트워크 장비 룰 점검을 명시적으로 추가하는 계기가 됨
