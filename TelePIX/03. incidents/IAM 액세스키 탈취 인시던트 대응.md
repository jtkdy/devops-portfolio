## 배경

GuardDuty 데일리 리포트를 매일 확인하는 루틴이 있었는데, 8월 12일 새벽 리포트에서 severity 9.0짜리 알림 발생
IAM 사용자 두 개의 액세스키가 외부에 노출된 정황, 공격자는 이미 새벽부터 활동 중

당시 S3 데이터 이벤트 로깅이 없었고 SSM 명령 내용도 CloudTrail에 기록되지 않는 구조라, 공격자가 어디까지 접근했는지 파악하는 데 시간 소요
이 사고를 계기로 로깅 체계 전반 재점검

## 접근

GuardDuty 알림을 기준으로 타임라인 먼저 정리
어떤 API가 언제 호출됐는지 CloudTrail에서 뽑아 공격자의 행동 패턴을 순서대로 재구성하는 방식으로 접근

피해 범위는 실제로 성공한 것과 차단된 것을 분리해서 확인
Secrets Manager 접근은 AccessDenied로 차단, EC2 생성이나 S3 버킷 생성도 실패했지만 S3 GetObject는 실제로 성공해 데이터 유출 확인

액세스키 비활성화는 서비스 영향을 먼저 확인하고 순차 처리
한꺼번에 다 끊으면 운영 중인 서비스가 영향받을 수 있어, 계정별로 하나씩 비활성화하며 서비스 상태 모니터링

## 구현

공격 흐름 정리
- 새벽 00:46 최초 탐지, 오후 13:39부터 본격적인 정찰 시작
- ListBuckets, ListSecrets, ListFunctions 등으로 전체 리소스 파악
- AssumeRole 16회 시도로 권한 상승 시도
- SSM SendCommand로 EC2 인스턴스 5대에 명령 실행 (내용 미확인)
- S3 GetObject 6건 성공 — 홈페이지 빌드 아티팩트 탈취
- 다음날 CloudTrail 로그 313건 복호화

조치는 아래 순서로 진행
1. CloudTrail 로그 버킷 외부 접근 차단
2. 노출된 액세스키 순차 비활성화
3. Terraform 상태 파일 버킷 접근 차단

## 결과

- Secrets Manager 접근 / EC2 생성 / S3 버킷 생성 — 전부 차단
- 실제 피해 — S3 빌드 아티팩트 6건 탈취, CloudTrail 로그 열람
- Terraform tfstate 접근 확인 — 데이터 이벤트 로깅 부재로 유출 여부 특정 불가
- SSM SendCommand 2건 — 명령 내용 미기록 + 이력 만료로 영구 확인 불가

## 회고

로깅 공백이 사고 대응을 얼마나 어렵게 만드는지 직접 체감
S3 데이터 이벤트 로깅이 없어 어떤 파일이 나갔는지 특정 불가, SSM 명령 내용도 기록이 없어 EC2에서 뭐가 실행됐는지 끝까지 확인 불가

액세스키 노출 경위도 결국 파악 불가
코드나 환경변수에 하드코딩된 키가 어딘가에 있을 가능성을 배제하지 못한 채로 마무리된 게 가장 찜찜하게 남음
이 사고 이후로 로깅 공백을 메우는 방향으로 우선순위 세 가지로 정리

- **S3 데이터 이벤트 로깅 활성화** — 어떤 파일이 접근됐는지 특정 가능하도록
- **SSM 로깅 강화** — 명령 실행 내용을 기록에 남기도록
- **IAM 최소권한 재검토** — 권한 상승 시도의 여지를 줄이도록

세 항목 모두 이번 사고에서 드러난 "무슨 일이 있었는지 끝까지 알 수 없었던" 공백을 직접 겨냥한 조치
