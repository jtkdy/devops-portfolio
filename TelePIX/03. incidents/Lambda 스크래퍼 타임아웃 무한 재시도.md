## 배경

RDS 마이너 버전 자동 업그레이드가 있던 날, 영향도를 확인하려고 연결된 Lambda 함수들의 로그를 들여다보다가 업그레이드와는 무관한 기존 장애 발견
이모지 수집용 스크래퍼 Lambda가 하루 288건씩 에러를 내고 있었는데, 아무도 인지하지 못한 상태

## 접근

에러 로그를 시간순으로 추적
이 Lambda는 15분마다 실행되면서 미승인 메시지를 한 트랜잭션으로 몰아서 처리하는 구조였는데, 문제는 처리해야 할 미승인 메시지가 394건이나 적체
Timeout이 80초로 짧게 잡혀있어 394건을 한 트랜잭션 안에서 다 처리하기 전에 시간 종료, 트랜잭션이 롤백되면서 다음 실행(15분 후) 때 똑같은 394건을 다시 조회하는 패턴 반복
처리는 영원히 끝나지 않고 에러만 계속 쌓이는 구조

여기에 트리거 타겟에 오타(`:pord`)까지 섞여 있어 15분마다 별개의 호출 실패 에러까지 추가 발생
같은 Lambda에서 서로 다른 두 가지 원인의 에러가 동시에 적체

## 구현

두 함수를 비교해서 문제 범위 축소

| 항목 | 이모지 스크래퍼 | 게시글 스크래퍼 |
|---|---|---|
| Runtime | python3.9 (EOL) | python3.9 (EOL) |
| Timeout | 80초 | 80초 |
| 상태 | 하루 288건 에러 | 최근 1시간 에러 0건 — 정상 |

게시글 스크래퍼는 RDS 업그레이드와 무관하게 정상 동작 중, 이모지 스크래퍼만 별도의 사전 존재 버그로 확인
두 함수 모두 2023년에 EOL된 python3.9로 동작 중이라는 공통점도 발견

## 결과 (진행 중)

우선순위별로 조치 항목 정리

- 즉시: 트리거의 오타 타겟(`:pord`) 제거
- 단기: 배치 처리를 건별 커밋 또는 배치 사이즈 제한 방식으로 개선
- 단기: Lambda timeout 상향 검토
- 중기: 두 함수 모두 python3.9 → python3.13 런타임 업그레이드

이 문서를 정리하는 시점까지는 아직 조치 전 상태

## 회고

이 버그는 원래 확인하려던 것(RDS 업그레이드 영향도)과 전혀 다른 목적으로 로그를 보다가 우연히 발견
정기적으로 Lambda 에러율을 확인하는 대시보드가 있었다면 288건/일이라는 수치가 훨씬 일찍 잡혔을 텐데, 그런 상시 모니터링이 없다 보니 다른 작업을 하다가 우연히 발견된 셈
"타임아웃 → 롤백 → 재시도 → 동일 데이터 재처리"라는 패턴은 배치 처리 로직에서 꽤 흔하게 반복되는 실수인데, 건별 커밋이나 배치 사이즈 제한 없이 큰 단위를 한 트랜잭션으로 밀어붙이면 이런 식으로 조용히 무한루프에 빠질 수 있다는 걸 재확인
